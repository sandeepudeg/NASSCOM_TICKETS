# Tickets Folder Feature — Requirements Specification v2.1

> **Changelog from v2.0:** All gaps identified in the coverage review have been resolved. Items added or amended in this version are marked **★ NEW** or **★ AMENDED**. Where the problem statement was silent on implementation detail, industry best practice has been applied and is noted inline.

---

## Introduction

The Tickets Folder feature is part of a broader AI-powered intelligent ticket routing and resolution platform. The platform receives IT support tickets, classifies them into defined categories, routes them to the correct department, retrieves similar past tickets, and suggests resolution steps — all with tracked confidence scores and escalation logic. Users can additionally organise tickets into named folders for workflow management. This specification covers all layers of the system: classification, RAG-based retrieval and resolution suggestion, agentic escalation, folder management, infrastructure, security, observability, and the frontend UI.

---

## Glossary

| Term | Definition |
|---|---|
| **Ticket** | A unit of work representing a support request, bug report, or task item. May be submitted as free text, structured JSON, a log snippet, a trace extract, or a metrics alert payload. |
| **Category** | One of the seven predefined routing destinations: Infrastructure, Application, Security, Database, Storage, Network, or Access Management. |
| **Folder** | A named container that groups one or more tickets together for workflow organisation. |
| **Folder_Manager** | The system component responsible for creating, updating, deleting, and listing folders. |
| **Ticket_Assignment_Service** | The system component responsible for assigning and removing tickets from folders. |
| **AI_Classifier** | The system component responsible for classifying tickets, routing them, retrieving similar past tickets, and suggesting resolution steps using an LLM and RAG pipeline. |
| **RAG_Engine** | The subcomponent of AI_Classifier that retrieves semantically similar past tickets and generates resolution suggestions from them. |
| **Resolution_Suggestion** | A ranked list of actionable steps generated by the RAG_Engine from similar resolved past tickets. |
| **Confidence_Score** | A float in [0.0, 1.0] representing the AI_Classifier's certainty about its routing decision. |
| **Escalation** | The act of flagging a ticket for mandatory human review when Confidence_Score falls below the escalation threshold. |
| **Pattern_Detector** | The subcomponent that identifies repeated issues across tickets within a sliding time window and recommends automation. |
| **LLM-as-Judge** | An evaluation method in which a second LLM instance scores the routing and resolution quality of the AI_Classifier on a held-out test set. |
| **User** | A person interacting with the system through the UI. |
| **API_Gateway** | The network component that routes, authenticates, and load-balances inbound HTTP requests to backend services. |
| **Auth_Service** | The system component responsible for authenticating users and enforcing role-based access control. |
| **Object_Store** | The system component responsible for storing documents, logs, and model artefacts. |
| **Vector_Store** | The system component responsible for storing and querying embedding vectors for semantic search. |
| **Soft Delete** | A deletion strategy where a record is marked as deleted but not physically removed from the database, enabling recovery and audit. |
| **RFC 7807** | IETF standard for machine-readable HTTP error responses (Problem Details for HTTP APIs). |
| **Causal Context** | Structured metadata extracted from logs, traces, or metrics that is correlated with a ticket to inform category routing and resolution suggestion. |

## Functional Requirements

### Requirement 1: Create a Folder

**User Story:** As a user, I want to create a named folder, so that I can group related tickets together.

#### Acceptance Criteria

1. WHEN a user submits a valid folder name, THE Folder_Manager SHALL create a new folder and return its unique identifier.
2. IF a folder name is empty or exceeds 255 characters, THEN THE Folder_Manager SHALL return a descriptive validation error.
3. IF a folder with the same name already exists for the user, THEN THE Folder_Manager SHALL return a duplicate name error.
4. THE Folder_Manager SHALL store the folder creation timestamp alongside the folder record.
5. THE Folder_Manager SHALL strip leading and trailing whitespace from folder names before validation and storage. IF the resulting name is empty after stripping, THEN a validation error SHALL be returned. ★ NEW
6. THE Folder_Manager SHALL reject folder names containing HTML or script injection payloads by applying server-side input sanitisation before persistence. ★ NEW
7. THE Folder_Manager SHALL enforce a maximum of 500 folders per user. IF this limit is reached, THE Folder_Manager SHALL return a descriptive limit-exceeded error. ★ NEW

---

### Requirement 2: List Folders

**User Story:** As a user, I want to view all my folders, so that I can navigate to the right group of tickets.

#### Acceptance Criteria

1. WHEN a user requests their folder list, THE Folder_Manager SHALL return all folders belonging to that user.
2. THE Folder_Manager SHALL return folders sorted by creation date in descending order by default.
3. WHEN a user has no folders, THE Folder_Manager SHALL return an empty list.
4. THE Folder_Manager SHALL support pagination via cursor-based page tokens, with a configurable page size defaulting to 50 and a maximum of 200. ★ NEW
5. THE Folder_Manager SHALL support an optional `name` filter query parameter that performs a case-insensitive prefix match against folder names. ★ NEW
6. THE Folder_Manager SHALL support sorting by `name` (ascending or descending) in addition to the default creation-date sort, controlled by `sort_by` and `sort_dir` query parameters. ★ NEW

---

### Requirement 3: Rename a Folder

**User Story:** As a user, I want to rename a folder, so that I can keep my organisation up to date.

#### Acceptance Criteria

1. WHEN a user submits a new valid name for an existing folder, THE Folder_Manager SHALL update the folder name and return the updated folder record.
2. IF the new folder name is empty or exceeds 255 characters, THEN THE Folder_Manager SHALL return a descriptive validation error.
3. IF a folder with the new name already exists for the user, THEN THE Folder_Manager SHALL return a duplicate name error.
4. IF the folder does not exist, THEN THE Folder_Manager SHALL return a not-found error.
5. THE Folder_Manager SHALL apply optimistic locking using a `version` field. The client SHALL supply the current version in the request. IF the version does not match the stored value, THE Folder_Manager SHALL return an HTTP 409 Conflict error. ★ NEW

---

### Requirement 4: Delete a Folder

**User Story:** As a user, I want to delete a folder, so that I can remove groupings I no longer need.

#### Acceptance Criteria

1. WHEN a user requests deletion of an existing folder, THE Folder_Manager SHALL soft-delete the folder by setting a `deleted_at` timestamp and return a success confirmation. The physical database record SHALL NOT be removed. ★ AMENDED
2. WHEN a folder is soft-deleted, THE Ticket_Assignment_Service SHALL remove all ticket-to-folder associations for that folder without deleting the tickets themselves.
3. IF the folder does not exist or has already been soft-deleted, THEN THE Folder_Manager SHALL return a not-found error.
4. Soft-deleted folders SHALL be excluded from all List Folders and View Tickets in Folder results by default. An authorised admin MAY supply `include_deleted=true` to retrieve them. ★ NEW

---

### Requirement 5: Assign a Ticket to a Folder

**User Story:** As a user, I want to assign a ticket to a folder, so that I can organise tickets into logical groups.

#### Acceptance Criteria

1. WHEN a user assigns a ticket to a folder, THE Ticket_Assignment_Service SHALL create an association between the ticket and the folder and SHALL record the `assigned_at` timestamp on the association record. ★ AMENDED
2. IF the ticket is already assigned to the specified folder, THEN THE Ticket_Assignment_Service SHALL return an already-assigned error.
3. IF the folder does not exist, THEN THE Ticket_Assignment_Service SHALL return a not-found error.
4. IF the ticket does not exist, THEN THE Ticket_Assignment_Service SHALL return a not-found error.
5. WHERE multi-folder assignment is enabled, THE Ticket_Assignment_Service SHALL allow a ticket to be assigned to more than one folder simultaneously. Multi-folder assignment SHALL be controlled by the environment variable `MULTI_FOLDER_ASSIGNMENT` (default: `false`). ★ AMENDED

#### Bulk Assign ★ NEW

6. THE Ticket_Assignment_Service SHALL expose a bulk-assign endpoint (`POST /api/v1/folders/{folder_id}/tickets/bulk`) that accepts a list of up to 100 ticket identifiers in a single request.
7. The bulk-assign endpoint SHALL process all assignments within a single database transaction. IF any individual assignment fails, the entire batch SHALL be rolled back and the response SHALL list the ticket identifiers that caused failures.
8. The bulk-assign endpoint SHALL return an HTTP 207 Multi-Status response body summarising successful and failed assignments when partial failures occur.

---

### Requirement 6: Remove a Ticket from a Folder

**User Story:** As a user, I want to remove a ticket from a folder, so that I can reorganise my ticket groupings.

#### Acceptance Criteria

1. WHEN a user removes a ticket from a folder, THE Ticket_Assignment_Service SHALL delete the association between the ticket and the folder.
2. IF the ticket is not assigned to the specified folder, THEN THE Ticket_Assignment_Service SHALL return a not-assigned error.
3. IF the folder does not exist, THEN THE Ticket_Assignment_Service SHALL return a not-found error.
4. THE Ticket_Assignment_Service SHALL leave the ticket record unmodified when removing it from a folder.

---

### Requirement 7: View Tickets in a Folder

**User Story:** As a user, I want to view all tickets inside a folder, so that I can work through a specific group of tickets.

#### Acceptance Criteria

1. WHEN a user requests the contents of a folder, THE Ticket_Assignment_Service SHALL return all tickets assigned to that folder.
2. WHEN a folder contains no tickets, THE Ticket_Assignment_Service SHALL return an empty list.
3. IF the folder does not exist, THEN THE Ticket_Assignment_Service SHALL return a not-found error.
4. THE Ticket_Assignment_Service SHALL return tickets sorted by `assigned_at` in descending order by default.
5. THE Ticket_Assignment_Service SHALL support pagination via cursor-based page tokens, with a configurable page size defaulting to 50 and a maximum of 200. ★ NEW
6. THE Ticket_Assignment_Service SHALL support sorting by `assigned_at` (ascending or descending) and by ticket `status`, controlled by `sort_by` and `sort_dir` query parameters. ★ NEW

---

### Requirement 8: Ticket Deletion Side-Effects ★ NEW

**User Story:** As a developer, I want well-defined side-effects when a ticket is deleted, so that no orphaned folder associations remain in the database.

#### Acceptance Criteria

1. WHEN a ticket is deleted from the system, THE Ticket_Assignment_Service SHALL automatically remove all folder associations for that ticket without deleting any folders.
2. The removal of ticket-folder associations on ticket deletion SHALL occur within the same database transaction as the ticket deletion to prevent orphaned records.

## AI / ML Requirements

### Requirement 9: Ticket Classification ★ AMENDED

**User Story:** As an IT support operator, I want incoming tickets automatically classified into a defined category, so that they can be routed to the correct team without manual triaging.

#### Acceptance Criteria

1. THE AI_Classifier SHALL classify every incoming ticket into exactly one of the following seven categories: **Infrastructure**, **Application**, **Security**, **Database**, **Storage**, **Network**, or **Access Management**. ★ NEW
2. THE category definitions SHALL be as follows, and SHALL be used as few-shot examples in the classifier prompt: ★ NEW
   - **Infrastructure** — issues with servers, virtual machines, compute resources, OS-level failures, or hardware.
   - **Application** — bugs, crashes, performance issues, or feature failures within a software application.
   - **Security** — threats, vulnerabilities, access anomalies, malware alerts, or compliance violations.
   - **Database** — query failures, replication lag, corruption, schema issues, or database connectivity problems.
   - **Storage** — disk full events, NAS/SAN failures, object storage errors, or backup failures.
   - **Network** — connectivity loss, latency spikes, DNS failures, firewall rule issues, or VPN problems.
   - **Access Management** — account lockouts, permission errors, SSO failures, or provisioning requests.
3. THE AI_Classifier SHALL assign a `confidence_score` (float, 0.0–1.0) to every classification decision and include it in the API response. ★ AMENDED
4. THE AI_Classifier SHALL use an open source SLM or LLM — such as Mistral 7B, Phi-3-mini, or Gemma 2B — served locally via Ollama with no external API dependencies.
5. THE AI_Classifier SHALL use open source sentence-transformer embedding models (e.g., `all-MiniLM-L6-v2`, Apache 2.0) to produce vector representations of ticket content for classification and similarity search.
6. WHEN a new ticket is submitted, THE AI_Classifier SHALL return a category and confidence score within 5 seconds under normal load (fewer than 100 concurrent submissions).
7. IF the AI_Classifier is unavailable or does not respond within the 5-second window, THE system SHALL NOT block ticket submission. The ticket SHALL be created with `routing_status: pending_classification` and queued for asynchronous retry with exponential backoff (initial delay 5 s, max 3 retries). ★ AMENDED

> **Best practice applied (AC 2):** Explicit category definitions with examples reduce LLM ambiguity and are standard practice in prompt engineering for classification tasks (few-shot prompting per Brown et al., 2020).

### Requirement 10: Structured Input Ingestion — Logs, Traces, and Metrics ★ NEW

**User Story:** As an IT engineer, I want to submit tickets that include log snippets, distributed trace extracts, or metrics alerts, so that the AI_Classifier can use this structured context to improve routing accuracy.

#### Acceptance Criteria

1. THE system SHALL accept ticket payloads in the following input formats in addition to plain free text: ★ NEW
   - **Structured JSON logs** — log lines conforming to common schemas (e.g., ECS — Elastic Common Schema, or plain key-value JSON).
   - **OpenTelemetry trace extracts** — spans in OTLP JSON format, including `traceId`, `spanId`, `serviceName`, `statusCode`, and `errorMessage` fields.
   - **Prometheus-style metrics alerts** — Alertmanager webhook payloads including `alertname`, `labels`, `annotations`, and `startsAt`.
2. THE AI_Classifier SHALL extract a `causal_context` object from structured inputs containing: error codes, affected service names, severity levels, and timestamps. This object SHALL be passed to the LLM prompt alongside the ticket text to enrich classification. ★ NEW
3. THE system SHALL perform causal correlation: WHEN a ticket contains a log or trace payload with an error-rate spike or latency anomaly, THE AI_Classifier SHALL bias the confidence weighting toward the Infrastructure, Network, or Application categories as appropriate, and SHALL include a `causal_signal` field in the response describing the detected anomaly. ★ NEW
4. IF a submitted payload does not match any accepted format, THE system SHALL fall back to treating the full payload as plain text and SHALL include a `parse_warning` field in the response. ★ NEW
5. THE system SHALL provide a CLI ingestion script (`ingest_ticket.py`) that accepts a file path and format flag (`--format json_log | otlp_trace | prometheus_alert | text`) for batch submission without a UI. ★ NEW
6. WHEN a submitted payload matches a recognised format (JSON log, OTLP trace, or Prometheus alert) but fails schema validation (e.g., missing required fields such as `traceId` or `alertname`), THE system SHALL return an HTTP 400 response with an RFC 7807 error body. The `detail` field SHALL identify the format that was detected and the specific missing or invalid fields. The ticket SHALL NOT be created. ★ NEW

> **Best practice applied:** Accepting OTLP and Alertmanager formats aligns with the CNCF observability stack standard used across IT organisations. Causal correlation (symptom-to-cause mapping) follows the SRE discipline of structured incident analysis.

### Requirement 11: RAG-Based Similar Ticket Retrieval and Resolution Suggestion ★ NEW

**User Story:** As a support agent, I want the system to retrieve similar past tickets and suggest resolution steps, so that I can resolve common issues faster without searching manually.

#### Acceptance Criteria

1. WHEN a ticket is classified, THE RAG_Engine SHALL query the Vector_Store for the top-5 most semantically similar resolved past tickets using cosine similarity, with a minimum similarity threshold of 0.70. ★ NEW
2. THE RAG_Engine SHALL return a `similar_tickets` array in the classification response, each entry containing: ticket ID, title, category, resolution summary, and cosine similarity score. ★ NEW
3. THE RAG_Engine SHALL generate a `resolution_suggestion` — a ranked ordered list of up to 5 actionable steps — by passing the retrieved similar tickets' resolution summaries as context to the LLM with an instruction to synthesise the most applicable steps for the current ticket. ★ NEW
4. THE `resolution_suggestion` SHALL include a `source_ticket_ids` array referencing the past tickets used to generate it, enabling agents to verify the source. ★ NEW
5. IF fewer than 2 similar tickets exceed the 0.70 similarity threshold, THE RAG_Engine SHALL still return whatever matches exist but SHALL set a `low_retrieval_confidence: true` flag in the response and surface this to the agent via a UI warning. ★ NEW
6. THE RAG_Engine SHALL use LangChain (MIT) or LlamaIndex (MIT) as the orchestration framework for retrieval and generation.
7. THE system SHALL index all resolved tickets into the Vector_Store within 60 seconds of resolution being marked, so that they are available for future retrieval. ★ NEW

> **Best practice applied:** Minimum similarity threshold of 0.70 is a widely used starting point for semantic retrieval tasks (MTEB benchmark practices). Returning source IDs follows RAG transparency best practices to allow human verification.

### Requirement 12: Escalation and Human Review ★ AMENDED

**User Story:** As a support manager, I want uncertain or ambiguous tickets automatically escalated for human review, so that mis-routing is caught before it delays resolution.

#### Acceptance Criteria

1. WHEN a ticket's `confidence_score` is below the configurable escalation threshold (default: 0.65, range: 0.50–0.90, set via environment variable `ESCALATION_THRESHOLD`), THE AI_Classifier SHALL set `routing_status: escalated` and assign the ticket to the human review queue. ★ AMENDED
2. THE system SHALL notify the on-call reviewer via a configurable webhook (Slack-compatible or generic HTTP POST) when a ticket enters the escalation queue. ★ NEW
3. THE system SHALL provide a human-review interface where an authorised agent can: view the classifier's suggested category and confidence, view the `similar_tickets` list, accept the suggestion, or override the category with any of the seven defined categories. ★ AMENDED
4. Agent overrides SHALL be recorded with the overriding agent's user ID, the original suggested category, the corrected category, and a timestamp. These records SHALL be used as labelled training examples in the retraining pipeline. ★ AMENDED
5. THE escalation queue SHALL be sorted by ticket submission time (oldest first) by default, so that SLA breach risk is minimised. ★ NEW
6. WHEN the escalation webhook is unreachable or returns a non-2xx response, THE system SHALL retry delivery with exponential backoff (initial delay 10 s, multiplier 2×, max 3 retries). IF all retries are exhausted, THE system SHALL log a `webhook_delivery_failed` audit event and continue processing without blocking ticket escalation. ★ NEW

### Requirement 13: Repeated Issue Detection and Automation Suggestion ★ NEW

**User Story:** As a support manager, I want the system to detect when the same issue recurs repeatedly and suggest automating its resolution, so that the team can eliminate toil for known problems.

#### Acceptance Criteria

1. THE Pattern_Detector SHALL monitor resolved tickets over a configurable sliding window (default: 7 days, range: 1–30 days, set via environment variable `PATTERN_WINDOW_DAYS`). ★ NEW
2. WHEN 3 or more tickets within the sliding window share the same category AND a cosine similarity of ≥ 0.80 between their embedding vectors, THE Pattern_Detector SHALL classify them as a repeated issue cluster. ★ NEW
3. WHEN a repeated issue cluster is detected, THE system SHALL create a `PatternAlert` record and surface an automation suggestion in the UI, including: cluster size, representative ticket title, suggested runbook keyword, and a link to all tickets in the cluster. ★ NEW
4. The automation suggestion message SHALL read in the form: _"This issue has occurred N times in the past D days. Consider creating a runbook or automated remediation for: [representative title]."_ ★ NEW
5. An authorised admin SHALL be able to dismiss, snooze (with a duration), or acknowledge a `PatternAlert` via the UI or API. ★ NEW
6. All `PatternAlert` events SHALL be written to the audit log. ★ NEW

> **Best practice applied:** Similarity threshold of 0.80 for cluster membership is deliberately higher than the retrieval threshold (0.70) to reduce false positives in automation suggestions. The 7-day default window follows ITIL incident trend analysis practices.

### Requirement 14: AI Classifier Quality and Evaluation ★ AMENDED

**User Story:** As a data scientist, I want defined accuracy targets, a semantic similarity evaluation metric, and an LLM-as-judge pipeline, so that model quality is objectively measurable and comparable across versions.

#### Acceptance Criteria

1. THE AI_Classifier SHALL achieve a minimum **macro-averaged F1 score of 0.80** across all seven categories on the held-out test split before being promoted to production. ★ AMENDED
2. THE evaluation pipeline SHALL compute and report **per-category F1 scores** in addition to the macro average, so that category-level weaknesses are visible. If any single category F1 falls below 0.65, the model SHALL be flagged for targeted retraining on that category before promotion. ★ NEW
3. THE system SHALL compute a **semantic similarity score** for resolution suggestions using cosine similarity between the generated suggestion embedding and the ground-truth resolution embedding on the test set. The minimum acceptable mean cosine similarity SHALL be 0.72. ★ NEW
4. THE system SHALL implement an **LLM-as-judge evaluation** pipeline as follows: ★ NEW
   - A second instance of the locally hosted LLM (the "judge") SHALL be prompted to score each test-set prediction on two dimensions: routing correctness (1–5) and resolution relevance (1–5).
   - The judge prompt SHALL include the original ticket, the predicted category, the resolution suggestion, and the ground-truth category.
   - The pipeline SHALL produce a mean judge score for each dimension and SHALL fail promotion if either mean falls below 3.5 / 5.0.
   - The judge prompt template SHALL be version-controlled alongside the model artefacts in MLflow.
5. THE evaluation pipeline SHALL be fully automated and invocable via a single script (`evaluate_classifier.py`) that outputs a structured JSON report covering all metrics above. ★ NEW
6. THE system SHALL track all evaluation runs in MLflow, associating each run with the model version, dataset version, and all metric values. ★ NEW

> **Best practice applied:** LLM-as-judge with a 1–5 Likert scale follows the methodology established in MT-Bench (Zheng et al., 2023). Separate per-category F1 reporting follows the standard ML fairness practice of disaggregated evaluation.

### Requirement 15: Bias Detection and Ethical Awareness ★ NEW

**User Story:** As a data scientist, I want the classifier's outputs monitored for category bias and fairness issues, so that no ticket type is systematically under-served.

#### Acceptance Criteria

1. THE evaluation pipeline SHALL compute a **class imbalance report** for every training and test dataset, listing the sample count per category. IF any category has fewer than 100 samples in the training set, a data insufficiency warning SHALL be emitted and the category SHALL be flagged for targeted data collection. ★ NEW
2. THE system SHALL compute **equitable recall**: the difference between the highest and lowest per-category recall values SHALL not exceed 0.25 at the time of model promotion. If it does, retraining with class-weighted loss or oversampling SHALL be attempted before promotion. ★ NEW
3. THE system SHALL document known limitations of each promoted model version in a `MODEL_CARD.md` file committed to the repository, following the Model Cards for Model Reporting standard (Mitchell et al., 2019). The model card SHALL include: training data summary, per-category F1 scores, known failure modes, and recommended use constraints. ★ NEW
4. THE system SHALL log the predicted category distribution in production (rolling 24-hour window) and SHALL alert via the observability webhook if any category's share of predictions deviates by more than 20 percentage points from its training distribution, as this may indicate input drift. ★ NEW

> **Best practice applied:** The 0.25 equitable recall bound and model card requirement follow Google's Responsible AI practices. Production distribution monitoring follows MLOps data drift detection standards.

### Requirement 16: Model Retraining Pipeline ★ NEW

**User Story:** As a data scientist, I want a scripted, automated retraining pipeline that incorporates agent override labels, so that the classifier continuously improves from production feedback.

#### Acceptance Criteria

1. THE system SHALL provide a scripted retraining pipeline (`retrain_classifier.py`) that executes the following steps without manual intervention: download raw datasets from MinIO cache, apply PII scrubbing, merge agent override labels, split train/validation/test, fine-tune or prompt-tune the base model, evaluate against all metrics in Requirement 14, and register the new version in MLflow if all thresholds pass. ★ NEW
2. The retraining pipeline SHALL be triggerable manually and on a configurable schedule (default: weekly, configurable via environment variable `RETRAIN_SCHEDULE_CRON`). ★ NEW
3. Agent override labels collected per Requirement 12.4 SHALL be weighted 2× relative to dataset samples to reflect higher label quality. ★ NEW
4. THE system SHALL retain at minimum the 3 previous model versions in MLflow and SHALL support instant rollback to any previous version via a single CLI command (`rollback_classifier.py --version <run_id>`). ★ NEW
5. IF a retraining run is already in progress when the cron schedule fires, THE system SHALL skip the scheduled run and log a `retrain_skipped_concurrent` event. Manual triggers SHALL also be rejected with an HTTP 409 response if a run is active, including the active run ID in the response body. ★ NEW

> **Best practice applied:** 2× weighting for human-verified labels is a standard curriculum learning technique. Retaining 3 previous versions follows MLflow and Kubeflow production rollback best practices.

### Requirement 17: PII Scrubbing and Data Privacy ★ AMENDED

**User Story:** As a security engineer, I want all ticket content scrubbed of personally identifiable information before it enters the embedding pipeline or is stored in the Vector_Store, so that the system complies with GDPR, HIPAA, and India's DPDP Act.

#### Acceptance Criteria

1. THE system SHALL apply PII scrubbing to all ticket text and structured payloads before embedding generation or Vector_Store insertion, using Microsoft Presidio (MIT) or scrubadub (MIT). ★ AMENDED
2. The following PII entity types SHALL be detected and redacted by default: person name, email address, phone number, IP address, credit card number, national ID number (including Aadhaar), date of birth, and physical address. ★ NEW
3. Redacted entities SHALL be replaced with type-labelled placeholders (e.g., `[EMAIL]`, `[PHONE]`) rather than deleted, so that sentence structure is preserved for the LLM. ★ NEW
4. THE system SHALL log a redaction summary (entity types detected, counts) per ticket to the audit log without logging the original PII values. ★ NEW
5. THE PII scrubbing step SHALL be bypassed only in a designated test environment via the environment variable `DISABLE_PII_SCRUBBING=true`. This variable SHALL be blocked from being set in the production Dockerfile. ★ NEW

### Requirement 18: Transfer Learning and Cross-Domain Adaptability ★ NEW

**User Story:** As a product owner, I want the classifier designed to be adaptable to other domains without a full rebuild, so that the system can be extended to handle HR, finance, or facilities tickets in the future.

#### Acceptance Criteria

1. THE AI_Classifier SHALL be implemented as a configurable pipeline in which the category taxonomy is defined in a single external configuration file (`classifier_config.yaml`) rather than hardcoded. Adding a new category SHALL require only: adding an entry to `classifier_config.yaml`, providing at least 50 labelled examples, and running the retraining pipeline. ★ NEW
2. THE system SHALL include a domain adaptation guide (`DOMAIN_ADAPTATION.md`) in the repository documenting the steps to retrain the classifier for a new ticket domain, including example config and dataset format. ★ NEW
3. THE base embedding model SHALL be swappable via the `EMBEDDING_MODEL` environment variable without code changes, to allow domain-specific embedding models to be used for specialised verticals. ★ NEW

> **Best practice applied:** Configuration-driven taxonomy follows the open-closed principle — open for extension, closed for modification. This is standard practice in ML pipeline design.

### Requirement 19: AI/ML Performance and Efficiency ★ NEW

**User Story:** As an operator, I want defined performance and resource targets for the AI pipeline, so that I can plan infrastructure capacity and meet SLA commitments.

#### Acceptance Criteria

1. THE AI_Classifier inference pipeline (from ticket receipt to category + resolution suggestion returned) SHALL meet the following latency targets under normal load (fewer than 100 concurrent requests): p50 ≤ 2 s, p95 ≤ 4 s, p99 ≤ 6 s. ★ NEW
2. THE AI_Classifier container SHALL operate within a memory ceiling of 6 GB per instance when using a 7B-parameter quantised model (4-bit GGUF format). Larger models SHALL use a dedicated GPU node defined in the Kubernetes manifests. ★ NEW
3. THE RAG_Engine vector search (top-5 retrieval from Vector_Store) SHALL complete within 500 ms at p99 for a corpus of up to 1 million indexed tickets. ★ NEW
4. THE Pattern_Detector cluster analysis job SHALL complete within 5 minutes for a corpus of up to 100 000 tickets in the sliding window. ★ NEW
5. THE system SHALL support horizontal scaling of the AI_Classifier service by running multiple stateless Ollama instances behind the API_Gateway load balancer. The Kubernetes manifests SHALL include a HorizontalPodAutoscaler targeting 70% CPU utilisation with a minimum of 1 and maximum of 5 replicas. ★ NEW

> **Best practice applied:** 4-bit GGUF quantisation is the current standard for running 7B LLMs on CPU-only infrastructure. The 70% HPA target follows the Kubernetes SIG Autoscaling recommendation to leave headroom for bursty traffic.

### Requirement 20: Training and Evaluation Datasets

**User Story:** As a data scientist, I want the AI_Classifier trained and evaluated on well-known, openly licenced Kaggle datasets downloaded via a reproducible script, so that model quality is verifiable and the pipeline can be re-run without manual data preparation steps.

#### Acceptance Criteria

1. THE AI_Classifier SHALL be trained and evaluated using the following three Kaggle datasets, downloaded via kagglehub:
   - `adisongoh/it-service-ticket-classification-dataset` — primary dataset for ticket category classification training.
   - `tobiasbueck/multilingual-customer-support-tickets` — multilingual support ticket data for broader classification coverage.
   - `vipulshinde/incident-response-log` — incident response logs similar to ServiceNow for routing and escalation training.
2. THE system SHALL use kagglehub (Apache 2.0) as the sole dataset download utility, invoked as `kagglehub.dataset_download("<owner>/<dataset>")`.
3. THE system SHALL provide a scripted, fully automated dataset download and preprocessing pipeline such that no manual steps are required to reproduce the training data.
4. WHEN datasets are downloaded, THE Object_Store SHALL store the raw dataset files in MinIO so that subsequent training runs can reuse cached copies without re-downloading.
5. THE system SHALL document the licence of each dataset and confirm that all three licences are compatible with the project's open source requirements before the dataset is used in training.
6. The dataset licence review SHALL be completed and recorded in a `DATASET_LICENSES.md` file in the repository before the first training run. This file SHALL be reviewed and updated whenever a new dataset is added. ★ NEW

## Non-Functional Requirements

### Requirement 21: Application Layer

**User Story:** As a developer, I want the API layer built on a well-supported Python web framework, so that the team can iterate quickly and integrate cleanly with the Python AI/ML ecosystem.

#### Acceptance Criteria

1. THE system SHALL expose all Folder_Manager, Ticket_Assignment_Service, and AI_Classifier operations as a REST API implemented with FastAPI (preferred) or Flask.
2. THE Folder_Manager SHALL be implemented using Python 3.10 or later.
3. THE Ticket_Assignment_Service SHALL be implemented using Python 3.10 or later.
4. THE AI_Classifier SHALL be implemented using Python 3.10 or later.
5. THE system SHALL route all inbound API requests through an API_Gateway before they reach backend services.
6. THE system SHALL use only open source Python packages published on PyPI for all application dependencies.
7. ALL API endpoints SHALL be versioned under the URL prefix `/api/v{major}` (e.g. `/api/v1/folders`). Breaking changes SHALL increment the major version. Non-breaking additions SHALL be backward-compatible within the same version. ★ NEW
8. ALL API error responses SHALL conform to RFC 7807 (Problem Details for HTTP APIs), returning a JSON object with at minimum the fields `type`, `title`, `status`, and `detail`. ★ NEW
9. THE system SHALL enforce CSRF protection on all state-mutating endpoints (`POST`, `PUT`, `PATCH`, `DELETE`) using the `SameSite=Strict` cookie attribute combined with a synchroniser token pattern where applicable. ★ NEW

---

### Requirement 22: Code Quality and Modularity ★ NEW

**User Story:** As a developer, I want enforced code quality standards and a modular architecture, so that the codebase is maintainable and open to contribution.

#### Acceptance Criteria

1. ALL Python source files SHALL comply with PEP 8 style, enforced by Ruff (MIT) linting on every CI run. Violations SHALL block merge. ★ NEW
2. ALL Python functions and public methods SHALL include type annotations (PEP 484) and a docstring following the Google docstring convention. ★ NEW
3. Cyclomatic complexity of any single function SHALL not exceed 10, as measured by Radon (MIT). Functions exceeding this limit SHALL be flagged by CI and require refactoring or explicit exemption with justification. ★ NEW
4. THE codebase SHALL follow a layered architecture with the following top-level Python packages: `api` (FastAPI routers), `services` (business logic), `repositories` (database access), `ml` (AI/ML pipeline), and `schemas` (Pydantic models). Cross-layer imports SHALL only flow downward (api → services → repositories). ★ NEW
5. THE repository root SHALL include a `README.md` covering: project overview, architecture diagram link, local setup steps, environment variable reference, and how to run tests. ★ NEW
6. THE repository SHALL include an `ARCHITECTURE.md` document with a C4-level component diagram (can be a Mermaid diagram embedded in Markdown) showing how all services interact. ★ NEW

> **Best practice applied:** Layered architecture with enforced import direction follows the Ports and Adapters (Hexagonal Architecture) pattern, widely used in production Python services. The C4 model is the industry standard for communicating software architecture.

### Requirement 23: Database

**User Story:** As a developer, I want a relational database for structured ticket and folder data and a vector store for embeddings, so that the system can support both transactional queries and semantic search.

#### Acceptance Criteria

1. THE system SHALL use PostgreSQL 14 or later as the primary relational database for all ticket and folder records.
2. THE system SHALL enable the pgvector extension on the PostgreSQL instance to store and query embedding vectors within the same database, avoiding a separate vector database service for the default deployment.
3. WHERE a dedicated vector database is preferred, THE system SHALL support Qdrant or ChromaDB as an alternative vector store in place of pgvector.
4. THE Folder_Manager SHALL persist all folder records — including `name`, `owner_id`, `created_at`, `updated_at`, `version`, and `deleted_at` — in the PostgreSQL database. ★ AMENDED
5. THE Ticket_Assignment_Service SHALL persist all ticket-to-folder associations including the `assigned_at` timestamp in the PostgreSQL database. ★ AMENDED
6. IF the database connection is unavailable at startup, THEN THE system SHALL log a descriptive error and exit with a non-zero status code.
7. THE system SHALL use optimistic locking via a `version` integer column on all folder records. Every write SHALL increment the version; a mismatched version on update SHALL return HTTP 409. ★ NEW
8. THE system SHALL perform automated daily PostgreSQL backups using `pg_dump` (BSD/MIT licenced). Backups SHALL be stored in the Object_Store and retained for a minimum of 30 days. ★ NEW
9. THE system SHALL enforce a data retention policy: soft-deleted folder records and their association history SHALL be physically purged after 365 days by a scheduled cleanup job. ★ NEW

### Requirement 24: Object Storage and Model Registry

**User Story:** As an operator, I want a scalable object store for documents and model artefacts, so that the system can manage attachments, logs, and ML model versions independently of the database.

#### Acceptance Criteria

1. THE Object_Store SHALL use MinIO or any S3-compatible object storage service to store ticket attachments, exported logs, and model artefacts.
2. THE system SHALL use MLflow as the model registry for tracking, versioning, and serving AI_Classifier model artefacts.
3. THE system SHALL aggregate application and service logs into a centralised log store accessible without direct container access.
4. THE system SHALL use only open source tools published under an OSI-approved licence for all storage and registry components.

### Requirement 25: Infrastructure and Deployment

**User Story:** As an operator, I want the system containerised and orchestrated with standard tooling, so that it runs consistently across development, staging, and production environments.

#### Acceptance Criteria

1. THE system SHALL provide a Dockerfile for each service that builds a runnable, self-contained container image.
2. THE system SHALL provide a Docker Compose configuration that defines all required services — API, database, vector store, object store, auth service, Ollama, Jaeger, Loki, Grafana, and MLflow — for local development. ★ AMENDED
3. WHEN a Docker container starts, THE system SHALL be ready to accept requests without manual intervention.
4. IF a required environment variable is missing at container startup, THEN THE system SHALL log a descriptive error and exit with a non-zero status code.
5. WHERE production scaling is required, THE system SHALL support deployment to a Kubernetes cluster using standard manifests or Helm charts.
6. THE system SHALL support integration with a CI/CD pipeline by exposing health-check endpoints and producing machine-readable build and test output.
7. Health-check endpoints SHALL be exposed at `GET /health/live` (liveness — returns HTTP 200 if the process is running) and `GET /health/ready` (readiness — returns HTTP 200 only when the database and all required services are reachable). Both endpoints SHALL return a JSON body with `status` and `version` fields. ★ NEW

### Requirement 26: Observability and Monitoring ★ NEW

**User Story:** As an operator, I want structured metrics, distributed tracing, and centralised logging, so that I can diagnose production issues without direct container access.

#### Acceptance Criteria

1. THE system SHALL expose a Prometheus (Apache 2.0) compatible `/metrics` endpoint on each service, including: request count, error rate, and latency histograms per endpoint, plus AI_Classifier-specific metrics: `classifier_confidence_score_histogram`, `classifier_category_distribution_counter`, and `escalation_queue_depth_gauge`. ★ NEW
2. THE system SHALL use the OpenTelemetry SDK (Apache 2.0) for distributed tracing. Trace data SHALL be exported to a Jaeger (Apache 2.0) instance. ★ NEW
3. THE system SHALL emit structured JSON logs to a Loki (AGPL 3.0) instance, queryable via a Grafana (AGPL 3.0) dashboard. ★ NEW
4. THE system SHALL define the following latency SLOs for folder and ticket CRUD operations under normal load: p50 ≤ 100 ms, p95 ≤ 250 ms, p99 ≤ 500 ms. ★ NEW
5. A pre-built Grafana dashboard JSON SHALL be committed to the repository covering: request rate, error rate, p99 latency, classifier confidence distribution, escalation queue depth, and pattern alert count. ★ NEW
6. THE system SHALL document in `README.md` that Loki and Grafana are licensed under AGPL 3.0. Organisations with policies restricting AGPL software SHALL substitute Loki with an alternative OSS log aggregator (e.g., OpenSearch, Apache 2.0) and Grafana with an alternative OSS dashboard tool (e.g., Apache Superset, Apache 2.0). The observability stack SHALL be swappable via Docker Compose service substitution without code changes to the application services. ★ NEW

### Requirement 27: Security

**User Story:** As a security engineer, I want authentication, authorisation, and secrets management handled by dedicated open source components, so that the system meets enterprise security standards without vendor lock-in.

#### Acceptance Criteria

1. THE Auth_Service SHALL use Keycloak (Apache 2.0) or Authentik (MIT) as the OAuth2/OIDC identity provider to authenticate all users before granting access to any API endpoint.
2. THE system SHALL enforce Role-Based Access Control (RBAC) with the following roles: `viewer` (read-only), `agent` (classify, resolve, override routing), `manager` (view pattern alerts, manage folders), and `admin` (all operations including soft-delete recovery and include_deleted queries). ★ AMENDED
3. THE system SHALL manage secrets using python-dotenv or python-decouple for local development, and Infisical (MIT licenced, self-hosted) for production; secrets SHALL NOT be committed to source control.
4. THE system SHALL encrypt all data at rest using AES-256 or equivalent.
5. THE system SHALL enforce TLS 1.2 or later for all data in transit between clients and the API_Gateway.
6. THE system SHALL enforce per-user rate limits at the API_Gateway: 300 requests per minute for standard users, 1 000 requests per minute for service accounts. Requests exceeding this limit SHALL receive HTTP 429 with a `Retry-After` header. ★ NEW
7. Access tokens SHALL have a maximum lifetime of 15 minutes. Refresh tokens SHALL expire after 8 hours of inactivity. The UI SHALL transparently refresh tokens and redirect to login on refresh failure. ★ NEW
8. THE CI/CD pipeline SHALL run Bandit (Apache 2.0) for Python SAST and Semgrep (LGPL 2.1) for cross-language scanning on every pull request. HIGH-severity findings SHALL block merge. ★ NEW
9. THE CI/CD pipeline SHALL run Trivy (Apache 2.0) to scan container images for CVEs. CRITICAL-severity CVEs SHALL block image promotion. ★ NEW

### Requirement 28: Audit Logging ★ NEW

**User Story:** As a security engineer, I want an immutable audit trail for all folder, ticket-assignment, classification, escalation, and override operations.

#### Acceptance Criteria

1. THE system SHALL write an audit log entry for every: folder create/rename/delete, ticket assign/unassign/bulk-assign, ticket classification, escalation, agent override, pattern alert creation/dismissal, and model promotion. Each entry SHALL capture: actor user ID, action type, target resource ID, timestamp (UTC), source IP, and relevant metadata (e.g., original vs corrected category for overrides). ★ NEW
2. Audit log entries SHALL be stored in a dedicated append-only `audit_log` table in PostgreSQL, protected by a row-level security policy that blocks `UPDATE` and `DELETE`. ★ NEW
3. Audit logs SHALL be retained in the primary database for 12 months, then archived to the Object_Store for a further 5 years. ★ NEW

### Requirement 29: Network and Inter-Service Communication

**User Story:** As a platform engineer, I want well-defined inter-service communication protocols and a managed API gateway.

#### Acceptance Criteria

1. THE system SHALL use REST over HTTPS as the default protocol for inter-service communication.
2. WHERE low-latency or streaming inter-service calls are required, THE system SHALL support gRPC as an alternative transport.
3. THE API_Gateway SHALL be implemented using Traefik (Apache 2.0) or Nginx (open source edition) for routing, rate limiting, and load balancing.
4. WHEN two internal services communicate directly, THE system SHALL enforce mutual TLS (mTLS) to authenticate both parties.

### Requirement 30: Testing ★ NEW

**User Story:** As a developer, I want a defined test coverage baseline and automated test execution in CI, so that regressions are caught before reaching production.

#### Acceptance Criteria

1. THE system SHALL maintain a minimum of 80% line coverage across all Python backend services, measured by pytest-cov (MIT). Coverage reports SHALL be published as CI artefacts on every build. ★ NEW
2. THE system SHALL maintain a minimum of 75% line coverage across the React frontend, measured by Vitest (MIT) with v8 coverage. ★ NEW
3. THE system SHALL include integration tests for each classification, retrieval, and resolution suggestion endpoint using a real PostgreSQL test container via testcontainers-python (Apache 2.0). ★ NEW
4. THE system SHALL include end-to-end browser tests for the critical user journeys using Playwright (Apache 2.0). ★ NEW
5. All tests SHALL be runnable in the Docker Compose environment without additional setup and SHALL produce JUnit XML output for CI integration. ★ NEW
6. THE system SHALL include property-based tests for the AI_Classifier pipeline using Hypothesis (MIT). The following properties SHALL be tested: (a) classification always returns exactly one of the seven defined categories regardless of input content; (b) `confidence_score` is always a float in [0.0, 1.0]; (c) bulk-assign always rolls back fully on any single failure (no partial commits). ★ NEW

### Requirement 39: AI Model Performance Dashboard ★ NEW

**User Story:** As a data scientist or admin, I want a dedicated AI model performance page in the UI that surfaces accuracy, evaluation, and quality metrics, so that I can monitor model health and make informed promotion decisions without querying MLflow directly.

#### Acceptance Criteria

1. THE UI SHALL provide an AI Model Performance page, accessible only to users with the `admin` or `agent` role, displaying the following metrics for the currently active model version: ★ NEW
   - Macro-averaged F1 score (with pass/fail indicator against the 0.80 threshold)
   - Per-category F1 scores displayed as a bar chart, with a visual warning on any category below 0.65
   - Mean semantic similarity score for resolution suggestions (with pass/fail indicator against the 0.72 threshold)
   - LLM-as-judge mean routing correctness score (1–5 scale)
   - LLM-as-judge mean resolution relevance score (1–5 scale)
   - Equitable recall spread (highest minus lowest per-category recall, with warning if > 0.25)
2. THE UI SHALL display a model version selector allowing the user to compare metrics across the last 3 promoted model versions side by side. ★ NEW
3. THE UI SHALL display a solution design summary panel showing: model name, embedding model in use, RAG framework, category taxonomy version, and a link to the `MODEL_CARD.md` for the selected version. ★ NEW

5. THE UI SHALL display a feasibility and system health panel showing: current escalation queue depth, pattern alert count, mean inference latency (p50/p95/p99), and classifier uptime percentage (rolling 24 hours). ★ NEW
6. THE UI SHALL display an innovation indicators panel showing: number of agent override labels collected (used in retraining), number of PatternAlerts raised in the last 30 days, and number of automation suggestions acknowledged by managers. ★ NEW
7. THE UI SHALL display a functional value and usability panel showing: mean time-to-classification (rolling 7-day), percentage of tickets auto-routed without escalation (rolling 7-day), and mean resolution suggestion acceptance rate (rolling 7-day, based on agent copy/use actions). ★ NEW
8. All metrics on this page SHALL auto-refresh at the same configurable interval as the main dashboard (Req 37.3). ★ NEW
9. WHEN any metric breaches its defined threshold (F1 < 0.80, semantic similarity < 0.72, judge score < 3.5, equitable recall spread > 0.25), THE UI SHALL highlight the metric card in amber and display a tooltip explaining the threshold and recommended action. ★ NEW

## Appendix A — Environment Variable Reference

| Variable | Default | Description |
|---|---|---|
| `MULTI_FOLDER_ASSIGNMENT` | `false` | Enable assigning a ticket to more than one folder simultaneously. |

| `RETRAIN_SCHEDULE_CRON` | `0 2 * * 0` | Cron expression for scheduled retraining (default: weekly, Sunday 02:00 UTC). |

| `DISABLE_PII_SCRUBBING` | `false` | Bypass PII scrubbing. Blocked in production Dockerfile. Test environments only. |
