Proposed Solution Architecture

AI-powered helpdesk system with intelligent ticket classification, RAG-based resolution, and continuous ML retraining pipeline.

This system ingests support tickets, scrubs PII, generates semantic embeddings, classifies tickets using a trained ML model, retrieves similar resolutions via RAG, detects recurring patterns, and routes tickets to appropriate agents — all while maintaining a full audit trail and retraining the model on new data.

Solution Architecture — Component View

Key Architectural Decisions

Intelligence Pipeline Design

All ML processing is encapsulated in backend/intelligence/. Each step (PII scrub → parse → embed → classify → RAG) is a separate service, allowing independent scaling, testing, and replacement. The classifier uses MLflow for versioning with a rollback mechanism.

Dual Database Strategy

SQLite (tickets.db) serves local development; Neon PostgreSQL (via .agents/skills/neon-postgres) serves production. The repository pattern in backend/repositories/ abstracts the data layer, making this seamless.

RAG for Resolution Hints

When a new ticket is submitted, rag_service.py queries the vector store for semantically similar resolved tickets. The top-k similar tickets and their resolutions are returned as hints to the agent, reducing mean time to resolution (MTTR).

Continuous Retraining Loop

The scripts/ml/ pipeline downloads Kaggle datasets, bulk-ingests them, backfills intelligence columns, retrains the classifier, evaluates it (see evaluation_report_retrained-*.json), and publishes the new model to MLflow with automatic rollback on quality degradation.

Intelligence Layer — Module Specifications

Intelligence backend/intelligence/pii_scrubber.py
  • Purpose: Detect and anonymise PII before any ML processing or storage
  • Techniques: Regex patterns for email, phone, SSN, credit card; NER (spaCy/presidio) for names and addresses
  • Input: raw_text: str → Output: scrubbed_text: str, pii_entities: List[PIIEntity]
  • Replacement strategy: Replaces PII with placeholders like [EMAIL], [PHONE], [NAME]
Intelligence backend/intelligence/structured_input_parser.py
  • Purpose: Normalise free-form ticket text into structured fields
  • Extracts: subject, body, urgency signals, affected system, reporter intent
  • Technique: Rule-based extraction + Ollama LLM for ambiguous cases
  • Output: ParsedTicket(subject, body, keywords, intent, affected_service)
Intelligence backend/intelligence/embedding_service.py
  • Purpose: Generate dense vector embeddings for semantic similarity search
  • Model: Ollama (local) with sentence-transformer compatible output (768-dim or 1536-dim)
  • Input: text: str → Output: embedding: List[float]
  • Caching: Embeddings cached in vector store; reused for duplicate/near-duplicate text
  • Used by: RAG service (similarity search) and classifier (feature input)
Intelligence backend/intelligence/classifier.py
  • Purpose: Multi-label classification — predicts ticket category, priority, and routing target
  • Model type: scikit-learn (RandomForest/SVC/LogisticRegression) trained on Kaggle + seeded data
  • Features: TF-IDF + embeddings as input features
  • Output: ClassificationResult(category, priority, assignee_group, confidence_score)
  • MLflow: Each trained model registered; loaded via MLflow model URI at startup
  • Rollback: scripts/ml/rollback_classifier.py reverts to last good version if evaluation degrades
Intelligence backend/intelligence/rag_service.py
  • Purpose: Retrieve-and-Generate resolution hints using vector similarity
  • Flow: embed(query) → vector_store.query(top_k=5) → filter by category → format resolution hints
  • LLM: Ollama used to synthesise top-k resolutions into a coherent suggestion
  • Output: RAGResult(similar_tickets: List, suggested_resolution: str, confidence: float)
Services backend/intelligence/escalation_service.py + pattern_detection.py
  • Escalation triggers: SLA breach, high priority + unassigned, repeated failure keywords, specific categories (security, data-loss)
  • Pattern detection: Groups similar tickets within a time window; if count > threshold, flags as recurring pattern and alerts
  • evaluation_service.py: Computes accuracy, F1, precision, recall on holdout set; writes evaluation_report_*.json

Data Engineering Pipeline

1

Ingestion — Download & Organise

scripts/ml/download_datasets.py fetches Kaggle datasets. organize_kaggle_folders.py restructures them into category-labelled directories. inspect_dataset.py validates schema against expected columns.

2

PII Scrubbing & Normalisation

pii_scrubber.py removes email, phone, names. structured_input_parser.py normalises text — lowercasing, stopword removal, tokenisation, extraction of key entities and urgency signals.

3

Feature Engineering

TF-IDF features extracted from scrubbed text. Dense embeddings generated via embedding_service.py (Ollama). Features combined into a feature matrix for classifier training. add_intelligence_columns.py DB migration adds the intelligence columns.

4

Bulk Ingestion to DB + Vector Store

scripts/ml/bulk_ingest_kaggle.py inserts processed tickets into the database. scripts/utils/populate_vector_store.py generates and stores embeddings in the vector store. backfill_kaggle_intelligence.py adds classification labels to historical data.

5

Model Training & Evaluation

scripts/ml/retrain_classifier.py trains the ML model on the current dataset, logs to MLflow with metrics. evaluate_classifier.py runs on holdout set, producing evaluation_report_*.json. Model promoted if metrics exceed thresholds.

6

Drift Monitoring & Rollback

scripts/ml/monitor_drift.py compares production prediction distributions against training baseline. On detected drift or performance degradation, rollback_classifier.py reverts to the last stable MLflow model version.

7

Database Maintenance

scripts/db/archive_audit_logs.py archives old audit records to keep the DB lean. scripts/db/purge_deleted_folders.py permanently removes soft-deleted folder records. scripts/db/backup_postgres.sh performs scheduled backups of production DB.

Entity Relationship Diagram

Data model showing all entities, attributes, and relationships inferred from the repository and model files.

Entity Descriptions

TICKET (core entity)

The central entity. Stores raw text, scrubbed text, parsed fields, ML-predicted category and priority, confidence score, embedding reference, status, assignee, SLA timestamps, and folder placement.

FOLDER

Hierarchical category/folder system (parent_id self-reference). Tickets are placed in folders based on their classified domain. Folders are managed via folder_repository.py.

AUDIT_LOG

Full change history for every ticket — who changed what, when, and from what value. Used for compliance, SLA tracking, and admin reporting. Old logs are archived periodically.

ML_MODEL

Registry of all trained classifier versions — links to MLflow run ID, accuracy, F1 score, deployment status. Enables rollback and A/B model comparison.

ESCALATION

Tracks escalation events for a ticket — triggered by SLA breach, manual agent request, or pattern detection. Stores escalation reason, target team, and resolution timestamp.

SIMILAR_TICKET

Pre-computed or on-demand similarity links between tickets, with cosine similarity score. Powers the RAG resolution hints feature and "related tickets" UI view.

Deployment Architecture

Local Development

Entry point: launch-dev.bat / run-local.sh — starts FastAPI + SQLite + Ollama (local LLM). Virtual environment: .venv_tickets/. Runs on localhost with hot-reload.

DB: SQLite (tickets.db) for zero-config local development.

Production (Containerised)

Docker: Multi-stage Dockerfile builds a lean production image. docker/ contains compose files.

DB: Neon serverless PostgreSQL (via connection string in .env).

Demo: deploy_hf_spaces.sh publishes to Hugging Face Spaces for public access.

Build & Package

Deploy

4

Post-Deploy Validation

verify_migration.sh confirms DB schema. validate_task_12_2.sh validates specific feature flags. Smoke tests confirm API health.
